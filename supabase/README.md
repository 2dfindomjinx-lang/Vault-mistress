# Database changes

schema.sql is the reviewed, non-personal legacy schema snapshot. It is not a complete migration history and must not be replayed blindly on production.

SQL files stay directly in this directory, following the existing project layout. Apply 202609090001_atomic_economy.sql before the corresponding API release. It is additive and safe to reapply. Existing balances are not changed by installation. Only service_role can execute the command or read its receipts/failure table.

Operational scripts stay ignored because some target real users; only the reviewed scripts named here are explicitly included in Git. Capture the deployed schema separately when database access is available; the local snapshot does not prove the production schema version.

Apply 202609090002_product_milestones.sql after the first migration for prospective product metrics. No historical milestones are fabricated; the first observed cohort includes returning users.

For the September 10 gameplay update, apply `202609100001_court_gameplay.sql` last, before deploying the new application. It requires the existing Gamble Hall engine. `gamble-hall.sql` is now included for isolated testing and initial setup; an existing installation does not need to replay it. If installing the engine from scratch, run `gamble-hall.sql` before the September 10 script. Replaying the engine later would replace the updated Patience functions, so always reapply the latest gameplay script afterward.

Existing installation order: `202609090001_atomic_economy.sql` → `202609090002_product_milestones.sql` → `202609100001_court_gameplay.sql`. If the first two have already run, only the third is new. No balances are changed by installing this script. Failed Court Games now permit another attempt; completed daily rewards remain locked. Patience targets are set before the wager and settle correctly even when the result is read late. The Jewelry Box multiplier is capped at the settlement engine's existing 250x ceiling so high-pick cashouts remain payable; the low-mine starting returns are unchanged. `npm run test:gameplay:sql` checks actual SQL in isolated PostgreSQL, including retries, ownership, countdowns and duplicate payouts.

The next September 10 fixes use `202609100002_court_fixes.sql`, directly in this same directory. Apply it **after** `202609100001_court_gameplay.sql` and before deploying these fixes. If the previous scripts already ran, only this new file is needed; do not replay the older engine afterward. It updates the Jewelry Box profit thresholds (7 mines: third safe pick; 10 mines: second; 15 mines: first), excludes admins and hidden profiles from the Furnace board, and adds service-only Gamble analytics. Installation does not alter balances, purchases or existing round records. The existing Furnace feature tables/profile fields are required. `npm run test:gameplay:sql` now applies both September 10 scripts and verifies thresholds through actual cashouts, leaderboard exclusions and analytics totals.

Typing recovery, timeout display refresh, apostrophe matching, wheel layout, three-color Roulette, Plinko's zero bucket, manual Patience defaults, share copy and license revocation are application changes. Revoke retains the purchase record and blocks activation/Wallpaper requests; already activated offline Discipline copies cannot be remotely stopped by this web release.

Run npm run test:security for isolated route and PostgreSQL checks. They never load .env.local. A production release also needs npm run check:deployment in its deployment environment and a backup/restore check. No production SQL has been applied by this implementation.

Throne Debt automatic payments (September 11): run `202609110001_throne_attribution.sql`, then `202609110003_throne_debt_auto_payments.sql`, before deploying the application. If 0001 has already run, only 0003 is required. `202609110002_repair_throne_debt_attribution.sql` is an optional historical feed repair, not a prerequisite for automatic payments; it continues to attribute old events without paying installments. Keep these files directly in this directory.

`throne-debts.sql` is included for isolated tests and initial setup of the legacy debt tables. Existing installations already have these tables and do not need to run that base script again.

New whole-dollar plans preserve the total: $75 across four installments becomes $19 + $19 + $19 + $18. Version 0003 leaves existing installment amounts and manual approvals unchanged; version 0004 below amends legacy unpaid schedules. New verified TD-code payments accumulate against the earliest unpaid installments. Any excess after the last installment remains an auditable, unapplied receipt; it does not mint PM, Coins, or devotion. VM/PT/CK/P2 tribute and WL wheel payments keep their own routing.

Contract approval remains manual. Automatic payment applies to active/overdue contracts. Pending, paused, timeout, completed, historical, and overlapping manual-review payments are recorded for review rather than guessed or replayed. The migration establishes a per-contract cutoff once; re-running it does not reset that cutoff. A pending manual review or an as-yet-unmatched approval holds the receipt to avoid counting an already approved payment twice. Admin and user pages show those receipts and partial balances; the user page refreshes every 10 seconds while visible. `npm run test:throne-debt` checks the actual PostgreSQL functions, whole-dollar allocation, partial payments, duplicate delivery, rollback/retry, historical/manual overlap, permissions, and webhook routing without production credentials.

Contract overhaul and PM settlement: apply **`202609110004_throne_debt_contracts.sql` after 0003**, before deploying this UI/API. If 0001 and 0003 are already installed, only 0004 is new. Do not replay 0003 afterward: it would replace the PM-aware webhook allocation function. Existing PM and money-transaction tables are prerequisites. No production SQL has been executed by this change.

0004 preserves already approved installments and their timestamps. For legacy active/overdue/paused contracts, it rounds the outstanding total down to whole USD once and redistributes unpaid balances across the existing due dates. Example: a $75 contract with one manually approved $18.75 installment retains that approval, waives $0.25, and schedules $19 + $19 + $18. Original installment amounts, the waiver and amendment date remain recorded. It does not infer the actual cash received for old manual approvals. Timeout redemption amounts are excluded from this amendment.

PM payments use 1 PM = $1, are deducted atomically with installment settlement and the money ledger, and have idempotent receipt IDs. Users may pay the next installment, through any future installment, or the full balance. Existing Throne credits reduce the PM cost; subsequent TD payments account for PM credits. Pending manual reviews block PM payment to prevent paying twice. PM is available for active/overdue agreements; timeout redemption still requires manual review. No reward currencies are minted. The contract shows due dates, original/amended amounts, remaining balances, PM/Throne credits, manual reviews, and completed agreements in its archive.

`npm run test:throne-debt` also verifies the 0004 migration, preserved manual approvals, one-time waiver, mixed PM/Throne settlement, ownership, insufficient balance, stale quotes, duplicate requests, transaction rollback and permissions. `node scripts/throne-debt-browser-check.mjs` checks request previews, responsive contract layout, PM payment and early completion using mocked HTTP; it does not make live payments.
